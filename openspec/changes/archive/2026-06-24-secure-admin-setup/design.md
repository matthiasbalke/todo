## Context

The setup wizard is exposed without authentication while the instance has zero admin users. That is necessary for bootstrapping, but it means a fresh deployment that is reachable on a network can be claimed by the first person who loads `/setup`.

The current backend already gates setup on `AdminService.setupRequired()` and rejects setup-only endpoints once an admin exists. The missing control is operator proof during the initial setup-required window.

## Goals / Non-Goals

**Goals:**

- Require proof of server/operator access before first-admin setup can start.
- Keep the setup flow simple for self-hosted deployments and local development.
- Avoid storing the raw setup secret in the database or exposing it through unauthenticated status APIs.
- Preserve the existing WebAuthn first-admin flow after the secret check passes.
- Fail closed after an admin exists, even if a previously valid setup secret is submitted.
- Keep automated E2E setup practical by providing a test-only or deployment-controlled way for the test harness to know the setup secret.

**Non-Goals:**

- Replacing passkey/WebAuthn setup with a password or invite system.
- Building a full installer session, multi-admin approval process, or email-based bootstrap flow.
- Making the setup token recoverable through the UI.
- Persisting setup authorization across backend restarts.

## Decisions

1. Use an in-memory one-time setup secret generated by the backend.

   The backend generates a high-entropy random secret whenever setup is required and no current setup secret exists. It logs the raw secret to the backend console and keeps only a hash in memory for validation. If setup remains required after a backend restart, a new secret is generated and logged.

   Alternative considered: configure a static `SETUP_TOKEN` environment variable. This is easier to script, but it creates another long-lived secret operators must manage and rotate. It can still be added later for automation if needed.

   E2E implication: the Playwright setup flow must be able to obtain the accepted secret without scraping human-oriented logs. The preferred path is a test/deployment-controlled configured setup secret that is only enabled in the E2E environment, while production keeps the generated console-logged default.

2. Validate the secret before issuing WebAuthn registration options and before completing setup.

   Setup is a two-step WebAuthn flow. Checking only the completion endpoint would still let an attacker create temporary setup users and WebAuthn challenges. Checking both endpoints keeps all setup mutations behind the secret and prevents stale browser state from completing after the secret changes.

   Alternative considered: add a separate "unlock setup" endpoint that stores an HTTP session flag. That would reduce payload repetition but adds state that is easy to mis-handle during session invalidation. Sending the secret with the two setup calls is simpler and explicit.

3. Keep `/api/setup` status public but do not expose token details.

   The frontend needs to know whether setup is required so it can route to `/setup`. The response remains limited to `setupRequired`; it must not reveal whether a secret exists, its creation time, or any hint useful for guessing.

4. Treat a valid setup completion as consuming setup mode.

   Once the first admin exists, `setupRequired()` becomes false and all setup-only endpoints return `SETUP_NOT_REQUIRED`. The in-memory secret can be cleared after successful admin creation, but the primary guard remains the admin count.

5. Surface an operator-focused setup-secret field in the UI.

   The setup page asks for the setup secret shown in backend logs. The UI should make clear that the secret is not an account password and is required only for first setup.

## Risks / Trade-offs

- Lost console log secret -> The operator restarts the backend while setup is still required to generate and log a new secret.
- Public logs or hosted platform log readers could see the secret -> The secret is only valid while setup is required, is not persisted raw, and is useless after the first admin exists. Operators should still treat deployment logs as sensitive during bootstrap.
- Multiple backend replicas could generate different setup secrets -> For initial implementation, document/assume single-replica setup. If multi-replica bootstrap becomes required, add a configured setup secret or shared store.
- Brute-force attempts against the setup endpoints -> Use high entropy and constant-time comparison. Existing rate limiting is not in scope, but error responses should not reveal partial validity.
- Browser challenge outlives secret restart -> Completion re-validates the submitted secret and rejects stale setup attempts.
- E2E cannot complete first-admin setup because the generated secret is only visible in logs -> Provide an explicit E2E-only configured setup secret or equivalent test harness hook, and ensure it is disabled or absent in production defaults.

## Migration Plan

No database migration is required. Existing uninitialized deployments will require the newly logged setup secret before creating the first admin. Deployments that already have at least one admin remain unaffected because setup endpoints already return `SETUP_NOT_REQUIRED`.

Rollback removes the secret requirement from setup endpoints. Any partially created setup user without credentials follows the existing cleanup behavior in the setup flow.

## Open Questions

- Should a future automation path allow `SETUP_TOKEN` to be supplied by environment variable for non-interactive deployments?
- Should setup-secret failures be included in the future audit-log capability once unauthenticated security events are implemented?
- Should the configured setup secret be implemented now as an E2E-only/environment-controlled path, or should tests read the generated secret through a Spring test bean hook?
